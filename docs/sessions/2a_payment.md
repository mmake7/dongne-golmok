## 컨텍스트

### 형이 이미 결정한 사항

| 결정 | 내용 |
|---|---|
| 결제 컨셉 격상 | Anti-Scope에서 빼고 v2 핵심 기능으로 |
| 결제 PG | TossPayments (테스트 키 확보, 실제 통합은 v2) |
| 결제 모델 | A (단순 선결제) + B (예약 선결제). C (충전식)는 v3 |
| 대상 가게 | 모든 가게 선택 가능 (카드 가능한 가게도 OK) |
| 수수료 | v1·v2 무료. 광고/PR 모델은 v3 |
| v1 데모 표현 | 가게 카드에 작은 배지 + 가게 상세에 자세한 안내 |

### 형이 풀려는 통증

1. **트럭·노점**: 카드 단말기 부재. 현금만.
2. **1인 메이커·공방**: 단말기 비용·부가세 부담으로 회피.
3. **재래시장 가게**: 단말기 있어도 "카드 안 받습니다" 관행.
4. **시즌·이동형**: 상시 운영 X 라 단말기 필요성 낮음.

### 동네골목이 푸는 방식

- 사용자가 앱에서 미리 결제 → 가게에서 결제 화면 보여주고 물건만 받음
- 가게는 동네골목으로부터 정기 정산 (주 1회 또는 월 1회)
- 가게 카드 단말기 없어도 카드·간편결제 손님 받음

## 수수료 정책

- **v1·v2**: 동네골목 수수료 0%. 가게가 받는 금액 = 사용자가 결제한 금액.
- **v3**: 광고/PR 모델로 수익. 결제 수수료는 검토 영역(아직 미정).

이유: 동네골목의 1순위 미션은 "동네 가게가 살아남게" 함. 수수료는 가게의 마진을 깎아 미션과 충돌.

## 법적 검토 항목 (v2 진입 전 필수)

- 전자상거래법 준수 (선결제 매개자 의무)
- 가게 사업자 등록 정보 수집 동의서
- 환불 규정 (사용자 vs 가게 vs 동네골목 책임 범위)
- 부가세 처리 (동네골목이 매개자라면 가게 부가세 처리 부담은 가게)
- 개인정보 처리 (결제 내역 보관 기간)
- 분쟁 처리 절차 (사용자가 안 받았다고 주장 시)

## TossPayments 통합 노트 (v2)

- 테스트 환경에서 모델 A부터 검증
- 정산은 동네골목이 주체 (가게 → 동네골목 → 정기 정산)
- 가게별 정산 계좌 등록 필요
- 결제 위젯은 TossPayments 표준 사용 (직접 구현 X)

## Anti-Scope (결제 도입에서 안 할 것)

- 즉시 정산 (주 1회 / 월 1회만)
- 다양한 PG (TossPayments만)
- 외화 결제 (KRW만)
- 가상자산 결제 (X)
- 분할 결제 / 카드 할부 (v2 안정화 후 검토)
